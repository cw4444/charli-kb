# Sidequest Prototyping

Sidequest prototyping is a product-discovery pattern where small, low-permission experiments are built quickly and judged by whether people actually keep using them.

The pattern:

1. Build a rough prototype quickly.
2. Put it in front of real internal or external users.
3. Watch whether they return to it without persuasion.
4. Polish and productize what gets repeated use.
5. Let unused experiments die without ceremony.

This is valuable because it replaces speculative planning with behavior. A prototype that people keep using is stronger evidence than a roadmap argument.

The concept should not become an excuse for random motion. Sidequests are useful when the team can cheaply test a hunch and when adoption is visible. They become wasteful when no one records what was tried, why it mattered, or what happened.

## Anthropic-Style Sidequest Maxxing

The Anthropic/Claude Code version, as preserved here from the Cat Wu / sidequest-maxxing source trail, is not just "let people brainstorm." It is closer to:

- give people permission to spend an afternoon building a working thing;
- skip the normal approval loop for low-risk prototypes;
- show a demo instead of narrating status;
- let teammates dogfood it immediately;
- watch whether anyone voluntarily keeps using it;
- polish only the ideas that create repeated internal demand;
- let unused experiments die without shame.

That is why this pattern fits AI-native work. When agents can collapse the distance between hunch and prototype, the cheapest useful evidence is often a working demo. The question becomes less "can you justify this on a roadmap?" and more "does anyone use it tomorrow?"

The source trail claims Claude Code desktop work, todo-list behavior, and plugin experiments followed this shape: quick prototype, internal adoption, then productization. Those details should be treated as commentary/source-claim unless verified directly in a full transcript or primary Anthropic source. The durable concept is the workflow pattern, not the exact origin story for every feature.

## What Makes It Work

Sidequest prototyping needs an unusually low handoff cost. It works best when:

- designers can edit or ship code;
- engineers can make product calls;
- product managers can build prototypes;
- internal users are close enough to try the thing immediately;
- demos replace performative status updates;
- adoption is visible without a politics meeting.

This is "all walk, little talk" product discovery. It is not anti-planning forever. It is a way to let reality vote before the roadmap calcifies.

## Charli's Working Interpretation

This matches the personal AI-work pattern where useful workflows often emerge from low-stakes experiments rather than pre-planned tasks. A session that starts as "what can we make?" or "surprise me" can produce a durable tool because the agent lowers the cost of trying.

That does not mean every random idea deserves saving. The filter is repeated use. If the human comes back to it tomorrow, it may be a workflow. If not, it was a sidequest and can die cleanly.
